# Bruter API Debug Findings

## Date

- `2026-06-01`

## Goal

Debug Ollama API behavior on `bruter` from the server side and determine whether the observed IDE failures are caused by transport/API issues or by model behavior at the application layer.

## Server State

- Host: `kb-brootforce`
- Ollama service: `active`
- Ollama version: `0.24.0`
- Main endpoint: `http://bruter:11434`
- Service status at check time: healthy, accepting requests

## What Was Verified

### 1. Service Health

Confirmed on `bruter`:

```bash
systemctl is-active ollama
systemctl status ollama --no-pager --lines=40
ollama --version
journalctl -u ollama -n 200 --no-pager
```

Result:

- no crash loop
- no obvious server-side transport errors
- recent `/v1/messages`, `/api/chat`, and `/api/show` requests completed with HTTP `200`

### 2. Controlled Claude-Compatible API Tests

Two controlled `/v1/messages` tests were run locally against `http://bruter:11434`.

#### `gemma4:e4b` with full bounded task and `Write` + `Bash`

Observed response shape:

- returned structured `tool_use`
- first action was a `Bash` call with `ls -F`

This shows:

- the API path can return real structured tool calls
- `gemma4:e4b` is capable of starting a tool-driven flow under at least some prompt/tool conditions

#### `llama3.2:latest` with full bounded task and `Write` + `Bash`

Observed response shape:

- returned structured `tool_use`
- first action was a `Write` call
- proposed file content and context references were hallucinated and not grounded in the actual repository

This shows:

- the API path still returns proper structured tool calls
- `llama3.2:latest` is more prone to low-grounding behavior even when tool use is present

### 3. Raw Traffic Capture on `bruter`

Server-side plaintext HTTP was captured with:

```bash
tcpdump -i any -A -s0 -c 12 'tcp port 11434 and host 10.101.10.111'
```

The capture showed the exact request body for a controlled `gemma4:e4b` call:

```http
POST /v1/messages HTTP/1.1
Host: bruter:11434
Content-Type: application/json

{"model":"gemma4:e4b","max_tokens":256,"tools":[...],"messages":[{"role":"user","content":"Read the repository context and tell me the first command you would run. Use the Bash tool."}]}
```

The server returned HTTP `200` with a plain-text clarification response:

- it said repository context was missing
- it did **not** emit a `tool_use` block in that simplified case

This proves:

- the API transport is not silently rewriting the response into a clarification
- when a clarification appears, it is genuinely the model output returned by Ollama

## Key Finding

The `bruter` API path is functioning correctly at the transport level.

The main issue seen so far is **behavioral**, not **connectivity-related**:

- some prompts plus tool sets produce valid `tool_use`
- some prompts produce clarification-only text
- some models produce structured tools but low-quality grounded actions

## Interpretation

At this point, the likely failure boundary is one of:

1. model behavior under the exact IDE prompt/tool envelope
2. the specific request shape generated by `Claude Code for VS Code`
3. orchestration differences between direct API testing and IDE-agent sessions

It is **not yet supported** by evidence that:

- Ollama on `bruter` is dropping tools
- the Anthropic-compatible endpoint is corrupting responses
- network transport is the main cause of the observed clarification reply

## Recommended Next Debug Step

Repeat a real IDE run while capturing traffic on `bruter`:

```bash
ssh root@bruter 'tcpdump -i any -A -s0 -w /tmp/ide-run-llama32.pcap tcp port 11434'
```

Then compare:

- the exact request body coming from the IDE
- the exact raw HTTP response from Ollama
- the text shown in the IDE UI

That comparison will tell us whether the IDE client is:

- sending a weaker prompt than expected
- omitting important tool definitions
- adding system instructions that bias toward clarification
- or faithfully rendering a model-originated clarification

## Practical Summary

- `gemma4:e4b`: API can return real tool calls, but IDE run already showed clarification-only behavior once
- `llama3.2:latest`: API returns real tool calls, but grounding quality is suspect
- `qwen3:8b-q4_K_M`: good next candidate for direct IDE testing
- `qwen2.5-coder:7b-instruct-q4_K_M`: remains negative control

## Live IDE Capture: `run-002` on `llama3.2:latest`

The live capture for `run-002` added one crucial finding:

- the VS Code client first sends one or more `POST /v1/messages?beta=true` requests for session-title generation
- those title-generation requests include `tools: []`
- only after that does it send the larger task-bearing request with the actual session content and tool definitions

The task-bearing request included:

- the selected text from the run record
- the full bounded task prompt
- a large system envelope from the IDE/Claude harness
- tool definitions

Observed server behavior on the large task request:

- HTTP `200 OK`
- SSE streaming response
- `input_tokens: 3031`
- `output_tokens: 1`
- `stop_reason: end_turn`

Interpretation:

- the client is not failing to send the prompt
- the client is not failing to send tools
- `llama3.2:latest` is still not turning that real IDE request envelope into a useful agent step

This makes `run-003` on `qwen3:8b-q4_K_M` the highest-value next comparison.
